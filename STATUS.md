## Current target

The last two frame-rate patched functions that run in the clinic ([NEXT.md](NEXT.md)): `0x0183ac60`
(20 KB; every frame-rate patch changes a jump and a flag), then `0x02713870` (11.6 KB; its only
patch edit is broken in v1.09, [QUIRKS.md](QUIRKS.md)). The task manager's frame is done.

## Recent results

- `BB_TARGET_FPS` (30, 60, uncapped) does what the community frame-rate patches "30 FPS++",
  "60 FPS++" and "Uncap FPS++" do, in every replaced function they edit, and each part is
  checked against the patch itself (`tools/verify.py run --patch FILE:NAME --env ...`,
  [VERIFY.md](docs/VERIFY.md)). Measured on a real screen (2026-10-07, 2560x1440 at 165 Hz, all
  replacements hooked, `BB_TARGET_FPS=60` with "60 FPS++"): frame pacing median 16.67 ms, p99
  16.69 ms, no frame over 1.5x the median.
- The runtime fork now starts native: no upscaler, no jitter, full screen at the display's size.
  With its temporal upscaler (FSR 3, jitter on), the sky showed the lower half of the screen
  mirrored into it; at native it does not.
- Unattended runs reach gameplay: `tools/play_route.py` plays `game/routes/*.route` (pad
  presses, keyboard text, waits on on-screen text): `new_game.route` goes from the title through
  character creation to the contract (which saves), `continue.route` loads that save into
  Iosefka's Clinic.
- Call counting probes (`BB_PROBES`, `runtime/probe.c`) show which original functions a run
  reaches; `tools/patch_overlap.py` and `tools/reloc_refs.py` map patches to functions and find
  callers through relocated pointers.
- Nine fixed-step state methods of a Chalice Dungeon state machine are replaced and checked on
  edge cases; they need a save that reaches the Chalice Dungeons to be recorded in-game.
- [QUIRKS.md](QUIRKS.md): Ghidra hides the code after calls to the engine's fatal error.
- The frame-rate patches also rewrite shared constants in the data segment (for example the
  1/30 s step at `0x04d29170`), which unreplaced code reads too. `BB_TARGET_FPS` is meant to run
  together with the patch for the rest of the game, so `verify.py run --patch` now applies the
  patch to both sides.

## Known issues

- Recording every hooked function at once slows frames enough to crash the runtime in the
  opening cutscene (a guest fault or a bad GPU command packet). With recording off, all
  replacements run clean; runs record only the functions they need (`BB_CAPTURE_ONLY`).
- An intermittent GPU library assertion (bad PM4 packet) while a save loads, about 75 s into a
  run, with or without recent hooks; the next run is clean.
- Rare NVIDIA Xid 32 errors at Vulkan device creation; the run aborts before game code runs.

## Open questions (runtime)

- The CPU affinity mask of the main thread on a PS4 (`scePthreadAttrGetaffinity` on
  `scePthreadAttrGet(scePthreadSelf())`): the game's own C library counts its bits as the number
  of CPUs while it starts, so the value can shape how many worker threads the game makes. The
  boot stops there until the value is known from documentation or a measurement, not guessed.

## Pipeline health

`tools/smoke.sh` (record, verify and mutation-test the known-good clock function) passes.

- A ledger row now pins the inputs it ran, not just the code: `symbols/verification.csv` carries
  `cases_sha256`, a hash of the case files by name and content, written by `--record` (which
  refuses a directory with no cases). `source_hash` already tied a row to the replacement's source,
  so before this a claim of agreement could silently become a claim about different inputs. 580 of
  the 723 rows are pinned from captures in this checkout. The other 142, across 42 functions, carry
  `unavailable`: the cases were indexed from the `address` every case file names, and no directory
  for those functions holds the row's case count. That includes 20 of the 21 `verified` functions --
  their captures were recorded in an earlier checkout (2026-10-07) and are not here. The rows are
  not wrong; they are unpinnable here, and a `verified` function with a blank pin is an error, so
  the marker has to be a deliberate act and `--record` never writes it. Re-pinning those 20 means
  re-recording them, which is a new claim rather than the old one made stricter.
- The traced differential evidence has its own freshness check. `tools/make_review_packet.py`
  compares each catalog run's recorded `harness_sha256`, `verify_sha256`, `engine_sha256`,
  `instruction_trace_sha256` and `loader_sha256` against the files in this tree and reports the
  difference per field. Measured for the first time, all 528 `engine_zero_init_*` runs were stale
  on three of the five fields (one had been refreshed once); they were re-run against the current
  tools, 528 of 528 clean, and the packet regenerated. A verdict from a run made by an older
  harness describes the same code and a different measurement.

- None of the 622 edge-verified functions has a recorded case, so `tools/promote.py` cannot move
  one of them to verified: it needs `$BB_CAPTURES/<function>/*.json` from a real run, and nothing
  in the tree writes those (`../captures` does not exist; the per-function recorders were
  removed). The generic input capture in NEXT.md's runtime track is the unblocker, and it cannot
  record until the boot gets past `scePthreadAttrGetaffinity`. The other gate, an approved row in
  `symbols/reviews.csv`, is not the binding one. Until then the edge-verified count only grows;
  README carries the live figure.

  What that evidence does cover: `edge` already means "original image against replacement, same
  case, in two processes" — `verify.py run_cases` executes the executable with no replacement for
  the original side, so it is differential execution, not an expectation table. The stronger form
  is `tools/differential.py differential`, which adds instruction-level trace and CFG coverage; it
  needs an `abi.json` per fixture directory and a Phase 1 catalog (`tools/function_catalog.py
  --state ... build`). All 528 zero_init members pass it, 4/4 fixtures each, with
  `--trace-instructions`. It does not move a function up the ladder: the ladder is about where the
  inputs came from, and these inputs are still generated, not recorded in a run.
